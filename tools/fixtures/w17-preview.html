W2.4 + W2.5 — fluid container, a11y tokens, contrast sweep

W2 is the app-shell lane from docs/FRONTEND-DEV-PLAN.md. This commit is the CSS-only sub-tasks: a fluid container with a max-1440 width cap, the prefers-reduced-motion and :focus-visible tokens (already shipped in W1), and a contrast sweep that introduces a new --mm-ink-soft token for sub-12px text on colored backgrounds.

Fluid container (max 1440)

.mm-container caps the page content at 1440px wide, centres it, and gives it 24px of side padding (16px on mobile). .mm-container-fluid is the same but with no max-width cap — useful for boards and tables that should bleed to the edge of the screen but still want consistent side padding.

.mm-container — content stays inside this 1440px box, even on a 4K display.
.mm-container-fluid — full-bleed (no max-width), still has the 24px side padding.

Stacks (vertical rhythm)

Two new utility classes for the common "stack of panels" pattern. .mm-stack uses 16px gaps (the default page rhythm); .mm-stack-tight uses 8px (for sub-sections inside a panel).

Contrast sweep (W2.5)

The booking board's stay-range chips and the data-table / table-scroll <thead> labels now use --mm-ink-soft instead of --mm-muted for the 12px text. --mm-ink-soft is a darker blue-grey (#344558) that hits WCAG AA at 12px on the --mm-bg surface, where --mm-muted was a bit thin.

prefers-reduced-motion + :focus-visible

Both were shipped in W1 and verified still in place. The reduced-motion rule disables every animation/transition inside .mm-ui when the user has the OS-level setting on. The focus-visible rule paints a 3px brand-coloured outline around any mm-* element that receives keyboard focus (mouse focus doesn't trigger the outline). Test by tabbing through the page.

W2.1 — Sidebar icon-rail (68px) + active-item pill, persisted in localStorage

W2.1 is the sidebar icon-rail sub-task of the W2 (App shell) lane from docs/FRONTEND-DEV-PLAN.md. Three pieces: a 68px icon-only rail state, an active-item pill (already in the shell CSS, just verified to work in rail mode), and localStorage persistence so the user's choice survives page reloads. The fourth piece — module counters via existing AJAX endpoints with a 60s cache — is omitted per the plan's "only where an endpoint already exists" rule (no counter endpoints exist in the codebase).

Three nav modes (full / rail / hidden)

The shell supports three sidebar modes. Each is a class on <body> that the JS toggles via [data-mm-nav-toggle] click handlers. The choice is persisted in localStorage['mm-nav-mode'].

Full (default, 248-272px)

Full sidebar with text labels, the menu search filter, and the nav-mode picker. Recommended for desktop.

Rail (68px)

Icon-only rail. The 28px icon chip in each menu item becomes a 32px centered icon, the text label is screen-reader-only, the menu search is hidden. The active-item pill renders as a 1px bottom-border on the active item.

Hidden (0px)

The existing .mm-nav-collapsed state — the sidebar is fully hidden and the main content fills the viewport. The hamburger button in the topbar reopens it.

JS contract (mm-ui.js)

A new mm-nav-mode section in public/assets/custom_js/mm-ui.js handles the toggle:

// On init:
applyNavMode(readNavMode());  // reads localStorage['mm-nav-mode']

// On click of [data-mm-nav-toggle]:
//   if data-mm-nav-mode is set → jump to that mode
//   else → cycle full → rail → collapsed → full
applyNavMode(next);
writeNavMode(next);

The button emits no global event; it just toggles a class on <body> and lets the CSS rules in shell.css reshape the sidebar. The choice is local — no server round-trip — so the toggle feels instant.

What was omitted (and why)

The plan's fourth item — "module counters (arrivals/departures/due-today via existing AJAX endpoints, 60s cache)" — was omitted per the plan's "wire to existing endpoints, else omit" rule. A scan of module/Hotel/routes/web_hotel_ajax.php returned no counter-style endpoints (the existing AJAX routes are for room-by-category, booking-details, in-house guest info, room status updates, etc., but none that return a single counter number suitable for a sidebar badge).

If a sidebar counter system is needed, it would require:

  1. New backend endpoints: GET /api/sidebar/counters returning {arrivals: N, departures: M, due_today: K}.
  2. A <span class="mm-nav-counter"> in each menu item, populated by a JS poller on a 60s interval.
  3. An ETag / cache-bust on the booking/check-in tables so the counter refreshes on writes.

That's a W6 or later ticket (depends on the existing notification system in app/Services/AppNotificationService.php), not a W2 ticket.
